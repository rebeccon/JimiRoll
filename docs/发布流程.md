# 发布流程（JimiRoll）

> 这份文档写给"以后要发新版本"的自己。照做即可，不需要回忆。

---

## 0. 一图流

```
改代码 / 改条件
   ↓
dotnet build                     ← 编译 + 自动部署到游戏 mods，进游戏实测
   ↓
.\build.ps1                      ← 打出 dist\JimiRoll-<版本>.zip
   ↓
填 docs\发布前验收清单.md          ← 六类验收逐项跑一遍，把结果贴进去
   ↓
改 JimiRoll.json 的 version + 写 CHANGELOG
   ↓
git add -A && git commit && git tag -a vX.Y.Z
   ↓
git push && git push --tags
   ↓
把 zip 里的 JimiRoll 文件夹交出去（GitHub Release 附件 / 创意工坊 / 群文件）
```

---

## 1. 发布物是什么

```powershell
.\build.ps1            # 只打包
.\build.ps1 -Deploy    # 打包 + 同时部署到游戏 mods 目录
```

产物：`dist\JimiRoll-<版本>.zip`，解压后是一个 `JimiRoll` 文件夹：

```
JimiRoll/
  JimiRoll.dll        纯代码模组本体
  JimiRoll.pdb        调试符号（可选，出问题时方便定位）
  JimiRoll.json       清单（id / version / dependencies…）
  README.md           说明
  CHANGELOG.md        更新日志
  LICENSE             MIT
  Pause.cmd           临时暂停搜索的小工具
  docs/               设计文档 + 发布前验收清单
```

**交给用户的就是这个文件夹** —— 丢进 `Slay the Spire 2\mods\` 即可。

---

## 2. 发版前必须做的四件事

1. **跑一遍验收清单**：`docs\发布前验收清单.md` 里的 A~F 六类逐项过。
   尤其是「D 干净环境（只启用 JimiRoll）」和「E 真实存档交叉验证」这两项 ——
   它们是本模组唯一能证明"给出去的种子是对的"的手段。
2. **确认 `JimiRoll.json` 的 `version` 已经改了**（`build.ps1` 是照它来命名 zip 的）。
3. **写 `CHANGELOG.md`**（在 `## [未发布]` 下面加一节；发布时改成 `## [X.Y.Z] — 日期`）。
4. **打 tag**：`vX.Y.Z`。

## 3. 推送到 GitHub

远端：**<https://github.com/rebeccon/JimiRoll>**（SSH：`git@github.com:rebeccon/JimiRoll.git`）。
`origin` 已经配好了，**平时只需要最后那三行**。

### 3.0 首次推送之前：把 SSH 公钥加到 GitHub

`git push` 走的是 SSH。公钥在 `C:\Users\rebeccon\.ssh\id_ed25519.pub`：

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIBCg9tkR9I8+sjEuszsbD2tH/RvULsn1rdKmAUNzevcx 2103646802@qq.com
```

加到 GitHub：**头像 → Settings → SSH and GPG keys → New SSH key**
→ Title 随便写（比如 `Windows-JimiRoll`）、Key type 选 `Authentication Key`、粘贴上面这一整行 → Add。

验证（出现 `Hi rebeccon! You've successfully authenticated...` 就对了）：

```powershell
ssh -T git@github.com
```

> ⚠️ `~/.ssh/djy070516` 那把 RSA 密钥**带密码（bcrypt 加密）**，非交互场景用不了 —— 用 `id_ed25519` 就行。

### 3.1 首次推送（远端已经有一个自动生成的 LICENSE 提交）

远端仓库是用 GitHub 的模板建的，里面已经有一个只含 LICENSE 的提交，
和本地历史**没有共同祖先**（unrelated histories）⇒ 直接 `git push` 会被拒。
因为远端那个提交没有价值，直接**覆盖**掉最省事：

```powershell
$git = "C:\Program Files\Git\cmd\git.exe"   # 本机 git 不在默认 PATH 里

& $git push -u origin main --force     # ★ 首次：覆盖远端那个 LICENSE-only 提交
& $git push --tags                     # 把 v2.2.0 等 tag 一起推上去
```

> `--force` 会**无条件覆盖远端分支**，属于危险操作。这里安全是因为远端只有一个模板提交。
> 日常维护里**不要**再用 `--force`；实在需要时用更安全的 `--force-with-lease`。

想保留那个提交也可以，改用合并的方式（会多一个"两条根"的合并提交）：

```powershell
& $git pull origin main --allow-unrelated-histories
& $git push -u origin main
```

### 3.2 之后每次发版

```powershell
& $git add -A
& $git commit -F <写好的提交信息文件>     # PowerShell 没有 heredoc，长信息写文件里
& $git tag -a vX.Y.Z -m "vX.Y.Z：一句话"
& $git push && & $git push --tags        # ★ tag 不会跟着 push 自动走，必须单独推
```

> ℹ️ `git commit -m "多行信息"` 在 PowerShell 里会被拆开，所以长提交信息**写进文件**再用 `-F`。

### 3.3 只改了文档 / README，要不要重新发版？

**不用。** 判断标准是"**代码行为有没有变**"：

| 改了什么 | 要动版本号吗 | 要重新打包吗 |
|---|---|---|
| README / CHANGELOG / 注释 | ❌ 不变 | ✅ 要（zip 里含 README，重跑 `build.ps1` 让包里的说明同步） |
| 纯 bug 修复（对外行为不变） | ✅ 补丁号 +1（`2.2.0 → 2.2.1`） | ✅ 要 |
| 新增功能 / 改筛选条件 | ✅ 次版本号 +1（`2.2.x → 2.3.0`） | ✅ 要 |
| 改了不兼容的东西（如 manifest id、字段结构） | ✅ 主版本号 +1（`→ 3.0.0`） | ✅ 要 |

版本号只体现在 **`JimiRoll.json` 的 `version`** 里（`build.ps1` 照它命名 zip）。

#### tag 能不能挪？—— 一条硬规则

> **Release 还没发布 → 可以挪；一旦发布过 → 绝对不要挪。**

- **发布前**（只是推了 tag，GitHub 上还没有 Release、没人下载过）：
  挪过去是安全的，能让"tag 指向的源码"和"你要发出去的包"一致：

  ```powershell
  & $git tag -f -a v2.2.0 -m "v2.2.0：一句话"
  & $git push --force origin v2.2.0        # ★ 推 tag 的改写要用 --force
  ```

- **发布后**：别人可能已经按 tag 下载/引用了。这时**不要挪 tag**，改成发一个新版本号：

  ```powershell
  # 假设已发过 v2.2.0，现在只想补个文档改动
  # → 改 JimiRoll.json 的 version 为 2.2.1，再走一遍 build/commit/tag/push
  & $git tag -a v2.2.1 -m "v2.2.1：README 修正"
  & $git push && & $git push --tags
  ```

### 3.4 本沙箱环境的两个坑（只影响"由 AI 代推"）

| 现象 | 原因 | 绕过 |
|---|---|---|
| `Failed to connect to github.com port 443` | 沙箱不放行 github.com:443，但 **22 端口是通的** | 用 SSH（`origin` 已经是 SSH） |
| `sh.exe: fatal error - couldn't create signal pipe` | Git 用 `sh` 跑 `core.sshCommand`，而沙箱禁止创建命名管道 | 设 `$env:GIT_SSH="C:\Windows\System32\OpenSSH\ssh.exe"` 让 git 直接调 ssh |
| `Failed to add the host to the list of known hosts` | 沙箱不让写 `~/.ssh/` | 用 `-o UserKnownHostsFile=<工作区路径>`，或干脆 `StrictHostKeyChecking=no` |

## 5. 可以直接贴的发布说明（模板）

```markdown
## 基米roll种器 v2.2.0

固定的开局条件 + 自动筛种，装好就自己跑，不用管它。

**筛什么**
- 涅奥骨骰开局
- 骨骰给的两个遗物 = 松动羊毛剪 + 新叶
- 最终诅咒 = 愧疚
- 第一章【出怪房间占比】≤ 30%（越低越好；全服平均约 43%）

**怎么用**
1. 把 `JimiRoll` 文件夹丢进 `Slay the Spire 2\mods\`
2. 启用它，回一次主菜单 —— 它就开始筛了（储备 10 个，约 1 分钟）
3. 进「自定义开局」，种子框里已经自动填好了

**这一版的新东西**
- 筛选指标从「问号房间最多」改成「出怪房间占比最低」（实测问号数和怪物占比几乎不相关，
  问号最多的那一档反而最差）
- 交付前会在游戏主线程上复核种子，确保你拿到手的那一局真的达标
- 不依赖任何其它模组

**注意**
- `WorkerCount` 保持默认的 1，别开多线程（实测会让游戏崩）
- 详见 README 的「已知限制」

**不兼容/已知问题**
- 游戏版本要求 ≥ 0.111.0
```

## 6. 换游戏版本时怎么跟

| 组件 | 会不会因为游戏更新而失效 |
|---|---|
| 种子编解码 / 哈希 / 种子→RNG | ❌ 不会（运行时调用游戏自己的类） |
| 骨骰条件（遗物池顺序、Niche 前置消耗） | ⚠️ 只有游戏改了池子才需要跟（日志会自己报错） |
| 第一章地图 / 出怪占比 | ⚠️ 依赖 `"act_1_map"` 流名与 `StandardActMap` 构造签名 |

**每次游戏大更新后**，进游戏看日志：
- `[地图·自检] ✓✓ 6/6` 不过 → 地图构造签名或流名变了，要重新用 `_tools/QnProbe` 核对
- `[自研] ✓✓ 自检通过：13/13` 不过 → 骨骰池子/顺序变了
- `[地图] ✗ 可用` → 直接拒绝搜索（不会给错种子）

工具用法见 `docs/去RT2化方案.md` 的附录。
